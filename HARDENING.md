# Hardening ledger

State for the `harden-loop` skill. One row per iteration, appended. **Read this before probing anything** — rows marked *clean* or *not-a-bug* are what stops the loop from re-litigating settled ground.

Rows are never deleted, only updated in place when a finding is fixed. A *not-a-bug* row must carry its reasoning, or the next iteration will re-open it.

### Iteration 4 result

Seven regression tests added; suite 581 → 588 passing, mypy strict and ruff clean. Nothing on the hot path was touched — `usable_anchors` runs once per worker in the offline renderer, over a list of one anchor per flush.

Two things worth carrying forward:

- **This is the same root cause as iteration 7's `Runtime -1000000000000ns`, in a code path that fix could not reach.** `format_ns` guards every *rendered* duration; it cannot guard a duration that is computed as positive from a corrupt mapping. A chokepoint fix protects the values that pass through it and says nothing about the arithmetic upstream — so a defect closed at the renderer is worth re-asking at the derivation.
- **The §5b page read paid for itself again, and this time on the fix rather than the bug.** The repaired page put "the wall clock stepped mid-run" directly above "the shared time axis is exact". Both sentences were individually correct and the pair reads as a tool that cannot add up — the same failure as iteration 2's `Runtime ?` above `Host ?`. Neither was findable from the test suite.

### Iteration 4 result

Two regression tests added; suite 581 → 590 passing, mypy strict and ruff clean, golden files and overhead bounds unchanged.

This is the **third** instance of one recurring defect, and that pattern is now the most valuable thing in this ledger:

1. `CAVEATS` listed three superseded workers while the header said `Processes 1` (fixed before this loop began).
2. `Runtime n/a` said a figure was missing without saying the clock was why, or that phase totals were unaffected (iteration 2).
3. The cross-host clock bound sat 7,800 characters below the findings that rest on it (this iteration).

Each time the caveat was *present and correct* and in the wrong place. The lesson generalises past this codebase: **a conclusions-first page moves the reader's stopping point, and every caveat has to move with it.** Adding a findings block to the top of a page silently invalidated the placement of every disclosure below it — none of which had changed. When this loop next touches ordering or adds a summary section, re-run readability question 4 against every caveat, not just the new text.

### Iteration 3 result

Seven regression tests added; suite 576 → 581 passing, mypy strict and ruff clean, hot path unchanged (2,590 ns at `measure_cpu=False`, within noise of the 2,646 ns measured before the change).

This iteration asked a different question from the first two — not "what input breaks it" but "why would someone not use it, and is it accurate enough" — and the two findings are the two answers:

- **A whole class of RL workload was silently mismeasured.** An async inference server is the standard shape for batched policy inference, and it produced a plausible, wrong report. This is the first defect found in this project where the *right* fix was to report rather than repair: a per-task stack is the correct mechanism and the hot path cannot pay for it, so the honest move is to make the limitation loud and name the workarounds. Recording that as "fixed (reported, not repaired)" matters — a later contributor with a cheaper `contextvars` idea should find this row, not conclude the issue is closed.
- **A stated number that is 2× optimistic is an accuracy defect**, not a documentation nit. Overhead figures are load-bearing here: the whole pitch is "cheap enough to leave on for twelve hours", and a reader deciding where to put a phase does that arithmetic with the headline number.

### Iteration 2 result

Five regression tests added; suite 571 → 576 passing, mypy strict and ruff clean. The crash is the significant one: it was the *first* defect found in this project that took down the whole report rather than one figure, and the guard it defeated (`_read_worker`) was written specifically to prevent that class.

Two things worth carrying forward:

- **The sentinel choice was itself a readability finding.** `"?"` was the obvious pick and was wrong: this report already prints `Host ?` for an unknown host and `compare` uses `?` for a thin sample, so `Runtime ?` directly above `Host ?` read as one kind of gap in two places. `n/a` matches what the wait column already prints. Reusing a symbol that means something else on the same page is the readability equivalent of representing "unmeasured" as a valid value.
- **Type-guarding is not value-guarding.** `_read_worker` casts with `float()`/`int()` and catches `TypeError`/`ValueError`, which is complete against *structural* corruption and blind to semantic nonsense — `float("inf")` passes every check because it genuinely is a float. When probing a new parse path, ask what a hostile value of the *right type* does.

### Iteration 1 result

Seven regression tests added; suite 562 → 571 passing, mypy strict and ruff clean. Measured on the probe run: text report longest line **10,022 → 121** characters (the 121 is a 2**70 counter printed exactly, which is the intended contract), HTML report **39,587 → 19,724** bytes, timeline **84,384 → 54,899** bytes. That is the argument for the read being mandatory rather than advisory.

## Surfaces not yet probed

Ranked by where this codebase's damage lives — see the `harden-loop` skill's step 1 for the reasoning.

- **Corrupt worker artifacts — partly done (iterations 2 and 4).** Covered: non-finite and out-of-order timestamps, negative and inconsistent phase numbers, and a worker's own wall clock stepping mid-run. Structural corruption (truncated sidecar, missing key, wrong type, zero-byte file) was already defended and tested before this loop began. *Still unprobed:* two workers sharing a pid with different uuids.
- **Cross-host clock skew — the other half of iteration 4, and a different mechanism.** Iteration 4 catches a clock that moves *within* one worker, because its own anchors then contradict each other. Two hosts whose clocks are each internally consistent but disagree by an hour leave no such evidence in the anchors: the lanes are simply drawn an hour apart, every idle share collapses toward zero, and `alignment_accuracy_note` still tells the reader to "treat sub-millisecond gaps between hosts as noise". The only evidence in the data is in the *arrows* — a `wait_on` released long before the `signal` that released it — which `_latest_before` currently absorbs and `Arrow.delay_ns` clamps to `0`, so a grossly skewed pair reads as an instant release. Probe: a real two-host run (or two workers' sidecars relabelled and offset), then read what the findings claim.
- **Degenerate runs**: zero phases; a phase entered but never exited (crash mid-phase); zero-length run (does anything divide by wall time?); nesting past `MAX_DEPTH` (32); more than `MAX_PHASES` (4096) distinct paths.
- **Merge across attempts/hosts/workers**: counter extremes through `merge`; `sample_stride` taint propagation; heterogeneous hardware across hosts.
- **Lifecycle**: fork during an open phase; signal arriving inside an `io=True` boundary; `close()` out of order with several profilers chained; `atexit` interaction with a hard `os._exit`.
- **Renderer scale**: the `--max-spans` path and progress output under a genuinely large trace (gap #7 in `WITHLINEPROFILER_GAPS.md`).

## Relationship to `WITHLINEPROFILER_GAPS.md`

That document is a *feature* backlog from a real investigation — eight gaps where the library could not answer a question that was asked of it. This ledger is a *reliability* record: what breaks, what silently misreports, and what has been proven not to. They are complementary and neither supersedes the other. Several gaps there (notably #1 async device work unmarked, and #8 unstated denominators) are also readability defects and are worth reading alongside the `report-readability` skill.
